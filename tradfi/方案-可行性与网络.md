# TradFi 数据获取 —— 可行性与网络方案

> 目标：把 10 家交易所的 **股票 / 大宗商品 / 指数** 行情(成交量、持仓量、资金费率、价格)接入,
> 用于观察标的活跃度并比较各所在 TradFi 领域的占比。
> 本文档基于 **2026-07-07 多轮真实探测**(端点测试 + 备用域名 + **VPN 开/关对比**)得出,机器为国内网络。
> **2026-07-11** 增补本机 REST **拉取速度基线**(`_speed_probe.py`),便于上 VPS 后同脚本对照。

## 一、一句话结论

- **VPN 开启时**:约 **7 家** 公开 API 可用(OKX / Gate / Bitget / Coinbase / Kraken + HTX/MEXC 备用域名);Binance **451**、Bybit **403**
- **VPN 关闭(直连)时**:仅 **Gate + HTX(备用域名)** 稳定可用;其余 8 家超时 / DNS 失败 / 连接重置
- **治根**:东京/新加坡 **VPS** 跑 downloader;本机只读 JSON,与 VPN 开关解耦
- **企业合作**:Bybit(CFD/MT5 + geo)优先;Gate CFD 详情需鉴权;**Binance bStocks 已确认可走现货 API,不必为行情数据找合作**

## 三、网络问题诊断与治根方案

### 3.1 诊断(已实测)

**VPN 开启(Veee TUN 模式,无本地代理端口)**
- OKX / Gate / Bitget / Coinbase / Kraken 直连正常
- MEXC / HTX 主域名 SSL 失败 → 备用域名 `futures.mexc.com` / `api.hbdm.vn` 可通
- Binance **451**、Bybit **403** = 应用层地理封锁(VPN 出口 IP 被这两家拉黑)
- Crypto.com **SSL UNEXPECTED_EOF**

**VPN 关闭(国内直连)**
- 仅 **Gate** + **HTX(api.hbdm.vn)** 稳定可用
- OKX DNS 解析失败;Bitget/MEXC 连接重置;其余 **超时或拒绝**
- Binance/Bybit 从 451/403 变为 **超时**(链路层面连不上)

**共性**
- 451/403 = 按出口 IP 辖区判定;**企业 key 不能绕过**(见 3.3)
- 本机无论 VPN 开/关都**无法覆盖 10 家** → 需海外 VPS

### 3.2 治根方案(按彻底程度)

| 方案 | 效果 | 成本/难度 | 适用 |
|------|------|-----------|------|
| **① 海外 VPS(东京/新加坡)** | **10 家全直连,IP 干净稳定,可挂 cron** | ~5 美元/月 | **首选,生产级** |
| ② 备用域名 | HTX→`api.hbdm.vn`、MEXC→`futures.mexc.com` 已验证 | 零成本,已内置 | 立即可用 |
| ③ 本地代理端口 | 装 Clash/v2ray 暴露 http 端口 + 设 `HTTPS_PROXY` | 低 | 临时,本机开发 |
| ④ 企业专线/机构接入 | 交易所给白名单 IP/专用域名 | 需谈 | 配合①,提升限频/历史/CFD |

> **注意选区**:VPS 不要选美国(Binance 对美国 IP 同样 451);选**东京 / 新加坡**最稳。

### 3.3 企业 API 能否解决 geo 封锁?——不能(重要)

- 451/403 是**按 IP 所在司法辖区**判的。**企业/机构 API key 本身不改变你的出口 IP,因此不能绕过 geo 封锁**。
- 企业 API 真正的价值:**更高频率限制、更长历史、CFD/机构专属数据、专线接入**。
- 只有当交易所给你**机构专用域名 / IP 白名单 / colocation** 时,才可能连 geo 一起解决——这需要单独谈。
- 结论:**先用 VPS 解决出口 IP(治根),再用企业 API 提升深度与限频(增强)**,两者互补。

## 四、本机拉取速度实测(供 VPS 对照)

> **目的**:把本机「单请求延迟 + 有效吞吐」写成可复现基线,VPS 上用同一脚本复测后横向对比。
> **不是**家庭宽带测速(Mbps),而是 **REST 行情接口的真实往返体验**——全量下载时间几乎全由 **RTT × 请求次数 + 限流 sleep** 决定,包体本身往往只有几 KB~几百 KB。

### 4.1 测试环境与方法

| 项 | 值 |
|----|----|
| 时间 | **2026-07-11 23:53 +0800** |
| 机器 | 国内本机(与本文其余探测同一环境) |
| 代理环境变量 | `HTTPS_PROXY` / `ALL_PROXY` = **无** |
| 实际可达性 | OKX/Bitget/MEXC/HTX/Crypto.com/Coinbase/Kraken 等多数海外域可通 → **系统级 VPN/TUN 很可能仍在**(与「无代理环境变量」不矛盾) |
| 脚本 | `tradfi/_speed_probe.py`(无第三方依赖) |
| 轮次 | 每端点 **3 次**取平均;超时 45s |
| 原始结果 | `tradfi/speed_probe_result.json` |
| 本机墙钟 | 全部用例跑完约 **267 s** |

**指标含义**

| 字段 | 含义 |
|------|------|
| 发现 ms / KB / KB/s | 合约列表(instruments/contracts)整包:耗时、包体、有效吞吐 |
| K线 ms / KB / KB/s | 单标的较大日线页(尽量拉满一页历史)同上 |
| ms | **含 DNS + TLS + 首字节 + 收完 body** 的端到端耗时 |
| KB/s | `bytes/1024 ÷ (ms/1000)`;小包时 **看起来很低是正常的**(延迟占主导,不是带宽跑满) |

VPS 复测:

```powershell
cd /path/to/data-download/tradfi
python _speed_probe.py --rounds 3
# 对比本机 speed_probe_result.json 与 VPS 新生成的同名文件
```

**读数摘要(仅统计成功的 K 线页)**

- 成功所 **单次 K 线请求中位耗时约 1.7~3.4 s**(Bitget 最快 ~1.7 s,MEXC 最慢 ~3.4 s)

- 有效吞吐多在 **2~20 KB/s(K 线页)** / **25~230 KB/s(大发现包)** → 瓶颈是 **跨境 RTT + TLS**,不是本机千兆网卡

### 4.4 换算成「全量下载会有多慢」(本机量级估算)

下载器限流见 `_common.py`:`RateLimiter.min_interval_s ≈ 0.12 s`。  
但本机实测 **单次 HTTP 已 2~4 s**,限流几乎不是主因——**RTT 才是**。

粗算(阶段一:每标的 price + OI + funding,保守按「每标的有效 3 次成功请求」):

| 假设 | 公式 | 本机量级 |
|------|------|----------|
| 单请求 | 取成功 K 线中位 **~2.5 s** | — |
| 每标的 | 3 次 × 2.5 s ≈ **7.5 s**(未计重试/翻页) | — |
| 单所 50 个 TradFi 标的 | 50 × 7.5 s ≈ **6~7 分钟** | 仅一所、一日线回补一页 |
| 7 所串行 × 50 标的 | ≈ **45~60 分钟** | 未含 Binance/Bybit;未含多页历史 |
| 若每标的要翻多页历史 | 再 × 页数 | 本机可能数小时级 |

VPS(东京/新加坡)预期对照点:

1. **可达性**:Binance/Bybit 应从 451/403 → 200(这是治根,比「快多少」更重要)
2. **延迟**:同 URL 的 ms_avg 若降到本机的 **1/3~1/5**(例如 K 线从 ~2.5 s → **0.4~0.8 s**),全量墙钟大致同比例缩短
3. **大包发现**:MEXC/Kraken 发现包接近 1~2 MB,VPS 上 KB/s 应明显抬升;若 ms 降但 KB/s 仍低,说明仍是限流/CPU/JSON 解析而非带宽

## 五、哪些需要去申请企业合作

> **2026-07 更新**:币安官方回复 **bStocks 可用现货 API 下载**,与 crypto 现货同一套接口,**不必为 bStocks 行情单独申请企业/RWA integrator**。

### Binance bStocks — 现货 API(币安确认,无需企业合作)

bStocks 在交易所侧是 **Spot 交易对**(如 `TSLABUSDT`、`NVDABUSDT`),与 crypto 现货同一数据管道:

| 用途 | 端点 | 说明 |
|------|------|------|
| 枚举交易对 | `GET https://api.binance.com/api/v3/exchangeInfo` | 筛 base/quote 含 bStock 符号 |

| **批量历史(推荐)** | `https://data.binance.vision/data/spot/...` | 无需 API Key;**本机无 VPN 已 ping 通** |

与 RWA bapi(`bapi/defi/.../token/rwa/*`)的关系:**bapi 偏链上元数据/合规状态**;**行情与成交量走现货 API 即可**,不必为下载数据申请 integrator。

## 七、轻量测试(可反复运行)

### 7.1 可达性矩阵

脚本 `feasibility_test.py`:对每家做 **可达性 + 单标的取数** 的最小测试,打印可用性矩阵并写 `feasibility_result.json`。
无需第三方依赖,支持 `HTTPS_PROXY` 环境变量。

```powershell
cd E:\Code\data-download\tradfi

# 本机直接测(看哪些通/哪些封)
python feasibility_test.py

# 走代理/VPS 后再测一遍对比(例如 Clash)
$env:HTTPS_PROXY="http://127.0.0.1:7890"; python feasibility_test.py
```

**判读**:
- `reachable=OK` 且 `sample_rows>0` → 该所可用
- `451/403` → geo 封锁,需 VPS/机构
- `SSL/timeout` → 网络层,试备用域名或代理

### 7.2 拉取速度(本机 vs VPS)

脚本 `_speed_probe.py`:对每家测 **发现接口 + 较大 K 线页** 的耗时/包体/有效吞吐,写 `speed_probe_result.json`。
详细数字与对照表见 **第四节**。

```powershell
cd E:\Code\data-download\tradfi
python _speed_probe.py --rounds 3
```

**判读**:
- 重点看成功所的 **K线 ms**(本机基线约 1.7~3.4 s);VPS 应明显更低
- Binance/Bybit 本机 451/403 → VPS 应变 200,再比 ms
- 小包 KB/s 低不等于带宽差;以 ms 和「能否拉通」为主
